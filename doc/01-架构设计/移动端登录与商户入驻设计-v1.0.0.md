# 移动端登录与商户入驻设计

- 版本：v1.0.0
- 状态：讨论稿（待评审，未实施）
- 适用范围：OpenFindBearings.Taro（H5/RN/小程序）、OpenFindBearings.Mobile（BFF）、OpenFindBearings.Identity（认证中心）、OpenFindBearings.Api（业务与商户模型）
- 变更记录：v1.0.0 首次成文，固化两档用户、密码先行、多管理员、一人多商户、提名入驻、邮箱优先送达、注销守卫、三段契约对齐等决策。

## 1. 背景与目标

移动端要落地"登录 / 登出 / 注销账户"与"商户入驻 / 团队管理"。现状是：认证与业务用户分两库（Identity 拥有认证用户、API 拥有业务用户，靠 sub 关联），但注册/登录入口（Taro→BFF→Identity）未打通、短信网关是半成品、商户成员模型是"一人一商户"的单值列。本文给出第一期可落地的完整设计与分期。

核心原则：
1. 认证事实源永远在 Identity；业务事实在 API；同步方向单向（API 不反写 Identity）。
2. 用户由"注册"产生（Taro 自助注册），不是后台 create。
3. 一个自然人（一个 Identity 用户 / sub）可属于多个商户、在每个商户有不同角色。
4. 商户不设唯一管理员，可多管理员；平台超管作零管理员兜底。
5. 送达渠道与邀请机制解耦（邀请码/链接为核心，邮箱/OA 优先、短信/站内补充），不被短信网关卡死。

## 2. 术语与角色

- 认证用户（OIDC User）：Identity 拥有，以手机号为用户名，持有 sub。
- 业务用户（Business User）：API 拥有，AuthUserId=sub 关联，首次带 token 调 API 时 JIT 创建。
- 平台级角色（全局 RBAC）：Individual（普通用户）、Admin、SuperAdmin（平台运维）。
- 商户域角色（按商户维度）：MerchantAdmin（该商户管理员）、MerchantStaff（该商户员工）。
- 商户成员（Merchant Member）：(用户, 商户, 商户域角色) 的一条关系。

## 3. 用户两档模型

- 档 1 普通用户：注册并登录后，收藏 / 关注 / 浏览历史解锁可用；可发起"商户入驻"。
- 档 2 商户成员：通过入驻或受邀，成为某商户的 MerchantAdmin 或 MerchantStaff，管理该商户的在售商品、团队、资料。

两档是"同一 sub 用户逐步获得角色/成员关系"，不是两类账户。一个 sub 可同时是：普通用户 + A 商户管理员 + B 商户员工。

## 4. 数据模型

### 4.1 Identity 侧（认证）
- 维持现状：OIDC 用户（手机号为用户名）、client/scope/permission、device_id claim、realm→TenantId。
- 本期不改 OpenIddict 配置；仅补"公开客户端调用契约"文档（见 5.3）。
- 安全收尾（另见《Identity 安全收尾》实施，非本文重点但登录依赖）：改密/禁用/注销→吊销 token、刷新链路校验用户可用性、refresh 轮换。

### 4.2 API 侧（业务与商户）
新增成员表（多对多，成为"谁属于哪个商户、在该商户什么角色"的唯一事实源）：

| 字段 | 说明 |
|---|---|
| Id | 主键 |
| UserId | 业务用户 Id（=sub 映射后的 API User） |
| MerchantId | 商户 Id |
| Role | MerchantAdmin / MerchantStaff |
| Status | Active / Invited / Removed |
| InvitedBy / JoinedAt / RemovedAt | 审计 |
| 唯一约束 | (UserId, MerchantId) 唯一 |

变更：
- 废弃 `User.MerchantId` 单值列，迁移为一条 MerchantMember（Role=MerchantAdmin，视为原归属）。
- 商户域角色（MerchantAdmin/MerchantStaff）从"全局用户角色"迁移为"成员行上的角色"；平台级角色仍走全局 RBAC。
- 鉴权语义改为："用户 U 能否管理商户 M" = 存在 `MerchantMember(U, M, MerchantAdmin, Active)`。
- 现有读 `User.MerchantId` 的点（如 `DeriveRateLimitUserType`、各商户归属判断）改走成员表 + 当前商户上下文（见 7）。

### 4.3 邀请模型
扩展现有 StaffInvitation：
- 增加 `Role`（Admin/Staff）。
- 增加"提名入驻"类型（Nomination）：为"尚未存在的商户"提名首个管理员（见 6.2）。
- 保持"渠道无关"：生成 invite code / 带 token 的链接；送达方式（邮箱/OA、短信、站内待办）只是投递通道。

## 5. 登录 / 注册

### 5.1 凭据策略：密码先行，SMS 后补
- P0：用户名（手机号）+ 密码 注册与登录，走 Identity `password` grant，不依赖短信网关，先把链路跑通。
- P1：接短信网关后，开通 `sms` grant（登录即注册）；开发态可固定验证码 + 日志输出。
- 注册入口：Taro → BFF → Identity（Identity 建 OIDC 用户）；首次带 token 调 API 时 `UserContextMiddleware` JIT 建业务用户。

### 5.2 三段契约（必须逐字段对齐）
- Taro → BFF：
  - 注册 `POST /mobile/auth/register` { phone, password }（P0）；{ phone, code }（P1）
  - 登录 `POST /mobile/auth/login` { username, password, deviceId }；`/mobile/auth/login-sms` { phone, code, deviceId }
  - 发码 `POST /mobile/auth/send-code` { phone, type=register|login }
  - 刷新 `POST /mobile/auth/refresh` { refreshToken, deviceId }
- BFF → Identity（当前有断点，须补全）：
  - 必须带 `client_id=mobile-client`（公开客户端自报）
  - 必须带 `realm=openfindbearings`（否则 password/sms handler 租户关直接拒绝）
  - 必须带 `scope=api:mobile`（否则 token 无 aud=openfindbearings-api，API 全 401）
  - sms 参数名统一 `phone`/`code`（BFF 现发 username/sms_code，Identity 读 phone/code，须对齐）
- BFF 自身：`Identity:Audience` 由 `api:mobile` 改为资源名 `openfindbearings-api`；转发 API 时透传用户 access_token（现传 null）。

### 5.3 device_id 语义
- 客户端自报、服务端仅做"跨请求一致性比对"，防误用/串设备，不防伪造（文案不得承诺"防盗号"）。
- Taro 侧：本地生成随机 GUID，用 storage.ts 异步封装持久化（RN 无 getStorageSync），随登录/刷新携带；同一会话生命周期内稳定（登录不无条件覆盖）。

### 5.4 token 策略（Taro 侧）
- access_token 仅内存（不持久化，纠正现状 request.ts 落盘）；refresh_token 持久化。
- 401 → 刷新 → 重放；刷新需 single-flight（并发只刷一次，避免共用一次性 refresh_token 竞态）。
- 刷新失败（invalid_grant）→ 清态并跳登录，不静默降级成空数据。

## 6. 商户入驻

入驻入口提供两种模式，默认"自助当管理员"，可选"提名他人当管理员"。

### 6.1 模式 A：自助当管理员（默认，先做）
1. 已登录用户点"申请入驻"，填商户资料 + 资质 → 建 Pending 商户，申请人 = 该商户 MerchantAdmin（成员表写一行）。
2. Admin 后台人工审核 → 通过则商户 Active，申请人管理员生效。

### 6.2 模式 B：提名他人当管理员
1. 已登录用户点"申请入驻"，选择"指定他人为管理员"，填被提名人手机号（+ 商户基础信息草稿）。
2. 系统建"入驻提名"（draft 商户，未生效）+ 一条 `Role=MerchantAdmin` 的待接受邀请，送达被提名人（邮箱/OA 优先、短信/站内补充）。
3. 被提名人：
   - 已注册 → 下次登录见"待办提名" → 接受 → 由被提名人补全资料、走 Admin 审核。
   - 未注册 → 通过邀请链接/码注册 → 登录后见待办 → 接受 → 补资料。
4. 审核通过 → 商户 Active、被提名人 = MerchantAdmin、发起人 = MerchantStaff（默认；发起人可勾"仅推荐不加入"则不建成员行）。
5. 被提名人拒绝 / 超时未处理 → 提名失效；发起人可换人提名或改自助。

### 6.3 管理员与团队
- 多管理员：一个商户可有多条 MerchantAdmin 成员行；任一在职 admin 可邀请/移除 admin 与 staff。
- 下限守卫：商户须 ≥1 个 Active MerchantAdmin。移除/离职/注销导致将变 0 时拦截提示"先保留至少一名管理员"。
- 平台兜底：若商户因异常（如全部注销）变 0 管理员，平台超管可在 Admin 后台指定一名新管理员。

## 7. 当前商户上下文（一人多商户）

- 移动端提供"商户切换器"：一个用户名下多个 Active 商户时，选定"当前操作商户"。
- 请求携带 `X-Merchant-Id`（或登录时 JWT 带默认 active merchant）；BFF/API 据此鉴权"该用户在该商户的角色"。
- 仅属一个商户的用户：默认即该商户，无需手选。
- 游客/普通用户（无商户）：切换器隐藏。

## 8. 登出 / 注销账户

- 登出：清本地 token + 调 Identity 登出 + 吊销该会话 refresh_token（依赖 Identity 安全收尾）。
- 注销账户（用户自助）：
  1. Identity 软删该 OIDC 用户 + 吊销其全部 token。
  2. API 侧：该 sub 的业务用户标失效；其对"唯一管理员"的商户先做守卫——须有 co-admin 或先转让，否则阻止注销并提示。
  3. 保留业务数据（商户/在售）不物理删，仅解除归属。

## 11. 关键时序（文字）

- 注册登录（P0）：Taro 输手机号+密码 → BFF /auth/register 或 /auth/login → Identity 建/验 OIDC 用户 → 返回 access+refresh（带 aud=openfindbearings-api）→ Taro 存（access 内存/refresh 持久）→ 首个业务请求 → API UserContextMiddleware JIT 建业务用户。
- 入驻模式 A：登录用户填资料 → BFF /merchants/apply(self) → API 建 Pending 商户 + 发起人 MerchantAdmin 成员行 → Admin 审核 → Active。
- 入驻模式 B：发起人填被提名手机 → /merchants/nominate → 建 draft + Admin 邀请 → 邮箱送达 → 被提名人注册/登录 → 待办接受 → 补资料 → 审核 → 被提名人 Admin、发起人 Staff。
- 邀请成员：admin 在成员管理页输邮箱/手机+角色 → 生成邀请 → 送达 → 对方接受 → 建 MerchantMember(Staff/Admin)。
- 注销：设置→注销 → 二次确认 → Identity 软删+吊销 → API 标失效 + 唯一管理员守卫。

## 12. 边界规则汇总

1. 认证以 Identity 为准；业务以 API 为准；单向同步。
2. 商户须 ≥1 Active 管理员；0 时平台超管兜底。
3. 一人可多商户；角色按 (用户, 商户) 维度；操作须带当前商户上下文。
4. 提名可被拒绝/超时失效，发起人可改自助或换人。
5. 发起人默认成 Staff，可"仅推荐不加入"。
6. 注销遇唯一管理员须先转让/有 co-admin。
7. device_id 仅防误用不防伪造；短信未就绪前用邮箱/邀请码，不卡死。

## 13. 实施 To-Do（按先后顺序，每项可端到端验收）

> 原则：每个任务都要"端到端可验"（能演示一条完整链路），不攒半成品。P0 不碰商户模型即可独立交付登录。

### P0 · 登录/注册链路打通（不含商户）
- **T0.1 BFF→Identity 契约补全**（Mobile）
  - 做什么：`AuthClient` 所有 /connect/token 请求补 `client_id=mobile-client`、`realm=openfindbearings`、`scope=api:mobile`；sms 参数改 `phone`/`code`；BFF `Identity:Audience` 改 `openfindbearings-api`。
  - 怎么做：三处 FormUrlEncoded 请求体统一加字段；配置项走 appsettings/ConfigMap。
  - 验收：curl BFF `/mobile/auth/login`（密码）→ 拿到带 `aud=openfindbearings-api` 的 access+refresh；用该 token curl API 受保护端点返回 200（非 401）。
- **T0.2 Identity 密码注册端点可用**（Identity）
  - 做什么：确认/补 `password` grant + 一个"注册"入口（建 OIDC 用户，手机号为用户名）；注册期密码必填即可（免密注册留 P4）。
  - 验收：curl 注册 → 新 OIDC 用户入库 → 立即用该账号密码登录成功。
- **T0.3 BFF 暴露 register/login/refresh**（Mobile）
  - 做什么：新增 `POST /mobile/auth/register`；login/refresh 对齐字段（含 deviceId）。
  - 验收：经 BFF 注册+登录+刷新全链路 200。
- **T0.4 Taro 登录/注册页 + auth store 接线**（Taro）
  - 做什么：建登录/注册页（密码）；接死代码 `stores/auth.ts`；`config.ts` 补 LOGIN/REGISTER/REFRESH 路径；AuthGuard 落地。
  - 验收：真机/H5 注册→登录→"我的"显示已登录；未登录点收藏→弹登录门槛→登录后收藏可用。
- **T0.5 Taro token 策略**（Taro）
  - 做什么：access 仅内存（改 request.ts 不再落盘）、refresh 持久化；device_id 本地 GUID 经 storage.ts 持久、登录不无条件覆盖；401→single-flight 刷新→重放，失败清态跳登录不降级空数据。
  - 验收：并发触发 401 只刷一次；access 过期后无感续期；断网/刷新失败→回登录页而非白屏。

### P1 · 安全收尾 + 登出/注销（Identity 为主）
- **T1.1 令牌吊销/轮换**（Identity）：改密/重置/禁用/注销→吊销该用户 token；启用 `UseRollingTokens`；登出走 `/connect/revocation`。验收：禁用用户后其 refresh 立即换不到 access。
- **T1.2 刷新链路查用户状态**（Identity）：`HandleRefreshTokenAsync` 补 `CheckCanLoginAsync`。验收：被禁用用户刷新被拒。
- **T1.3 机密出源码**（Identity+部署）：SeedData 客户端 secret/证书密码改 K8s Secret 注入。验收：仓库无明文 secret、服务正常签发。
- **T1.4 Data Protection 密钥持久化**（Identity）：落持久卷/Redis。验收：Pod 重启后已登录 SSO 不掉线。
- **T1.5 登出/注销账户（移动端）**（Taro+Identity+API）：登出清态+调 Identity 登出；注销=Identity 软删+吊销+API 业务用户标失效+唯一管理员守卫。验收：注销后无法再登录、其收藏关注按合规处置、商户不出现 0 管理员。

### P2 · 商户成员模型 + 自助入驻（模式 A）
- **T2.1 MerchantMember 多对多表 + 迁移**（API）：建表(UserId,MerchantId,Role,Status)；`User.MerchantId` 迁成一行 Admin；全局 MerchantAdmin/Staff 角色改成员行角色。验收：存量商家/员工迁移后鉴权行为不变。
- **T2.2 当前商户上下文**（API+Taro）：`X-Merchant-Id`（或 JWT 默认 active）；`DeriveRateLimitUserType` 等改走成员表。验收：一人多商户时按所选商户鉴权。
- **T2.3 入驻模式 A（自助当管理员）**（API+BFF+Taro）：填资料→建 Pending 商户+发起人 MerchantAdmin→Admin 审核→Active。验收：移动端申请→Admin 通过→申请人成管理员可管该商户。
- **T2.4 商户切换器 UI**（Taro）：多商户可切换、单商户默认。验收：两商户间切换后操作作用在正确商户。

### P3 · 团队 + 提名入驻（模式 B）+ 多管理员
- **T3.1 成员管理 + 邀请**（API+BFF+Taro）：admin 邀请邮箱/手机+角色→邀请码/链接→对方接受→建 MerchantMember。验收：受邀人登录后成为 staff、能按角色操作。
- **T3.2 多管理员 + ≥1 守卫 + 平台兜底**（API+Admin）：任一在职 admin 可邀/移 admin&staff；移除致 0 admin 时拦截；超管可兜底指定。验收：删到最后一个 admin 被拦、超管可救。
- **T3.3 入驻模式 B（提名）**（API+BFF+Taro）：发起人提名他人手机→draft+Admin 邀请→邮箱送达→被提名人接受补资料→审核→被提名人 Admin、发起人默认 Staff(可仅推荐)。验收：提名→接受→入驻→双方角色正确；拒绝/超时可失效重提。
- **T3.4 送达渠道**（Identity/API）：邮箱(OA/SMTP)优先、站内待办、短信占位。验收：邀请邮件可达、点击进待办。

### P4 · 短信登录即注册（解除对短信网关依赖后的增强）
- **T4.1 短信网关接入**（Identity）：SendAsync 真发、开发态固定码+日志、日上限频控。
- **T4.2 SMS grant 打通**（Identity+BFF+Taro）：登录即注册、`phone`/`code` 全链路。
- **T4.3 免密注册（路径 A）**（Identity）：SignUp 密码改可选。
- 验收：手机号+验证码一键注册登录贯通；与密码登录并存。

### 依赖与顺序说明
- P0 完全独立于商户模型，先交付即得"可登录的移动端"。
- P1 的 T1.1/T1.2 是 P2/P3 商户鉴权与注销守卫的前置（注销守卫依赖吊销能力）。
- P2 依赖 P0（需登录态）；P3 依赖 P2（成员表）。P4 独立、最后做。
- 全程不改 OpenIddict 核心配置（仅补公开客户端调用契约文档）。
