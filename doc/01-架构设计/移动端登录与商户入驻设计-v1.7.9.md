## 1. 背景与目标

移动端要落地"登录 / 登出 / 注销账户"与"商户入驻 / 团队管理"。现状：认证与业务用户分两库（Identity 拥有认证用户、API 拥有业务用户，靠 sub 关联），注册/登录入口（Taro→BFF→Identity）已打通，商户入驻整体（成员表/审核门/入驻三模式/团队管理）已于 v1.2.0 对应周期落地。本文给出**落地后的权威设计**，作为前端（Taro）与 BFF 侧的对接依据。

核心原则：
1. 认证事实源永远在 Identity；业务事实在 API；同步方向单向（API 不反写 Identity，Identity 不查 API）。
2. 用户由"注册"产生（Taro 自助注册），不是后台 create。
3. 一个自然人（一个 sub）可属于多个商户、在每个商户有不同角色。
4. 商户不设唯一管理员，可多管理员；须 ≥1 管理员，平台超管作零管理员兜底。
5. 送达渠道与邀请机制解耦（邀请码/链接为核心，邮箱/OA 优先、短信/站内补充），不被短信网关卡死。
6. **保护 OpenIddict**：不改 grant/端点拓扑/租户模型/handler 逻辑；令牌吊销等只用 OpenIddict 提供的 Manager API 编程调用。

## 2. 术语与角色

- 认证用户（OIDC User）：Identity 拥有，手机号为用户名，持有 sub。
- 业务用户（Business User）：API 拥有，AuthUserId=sub 关联，首次带 token 调 API 时 JIT 创建。
- **鉴权事实源分工**：Identity 自管理台用 token 里的 role；**OpenFindBearings 业务鉴权不用 token role claim，一律查 API 自己的权限表/成员表动态判定**。JWT 的 role claim 不作为业务鉴权依据。
- 平台级角色（API 全局 RBAC）：Individual、Admin、SuperAdmin。
- 商户域角色（按商户维度，存于成员行）：MerchantAdmin、MerchantStaff。
- 商户成员（Merchant Member）：(用户, 商户, 商户域角色, 状态) 的一条关系，存 `MerchantMember` 表，一人多商户的唯一事实源。

## 3. 用户两档模型

- 档 1 普通用户：注册并登录后，收藏 / 关注 / 浏览历史解锁可用；可发起"商户入驻"。
- 档 2 商户成员：通过入驻或受邀，成为某商户的 MerchantAdmin / MerchantStaff，管理该商户在售商品、团队、资料。

两档是"同一 sub 用户逐步获得角色/成员关系"，不是两类账户。一个 sub 可同时是：普通用户 + A 商户管理员 + B 商户员工。用户级数据（收藏/关注/历史）挂 UserId、与商户上下文无关；商户级操作才需当前商户上下文（X-Merchant-Id）。

## 4. 数据模型（已落地）

### 4.1 Identity 侧（认证）
- 维持现状：OIDC 用户、client/scope/permission、device_id claim、realm→TenantId。
- **不改 OpenIddict grant/端点/handler/租户模型**。安全项仅通过 Manager API 编程实现（见 8）。
- 注册入口已存在：`POST /api/Account/signup`（AllowAnonymous），请求体 `SignUpRequest{ account, password, confirmPassword(必填), agreeTerms(必须 true), realm(必填), inviteCode? }`；signup 只返回 UserResponse、**不返回 token**。

### 4.2 API 侧（业务与商户）
- **MerchantMember 成员表（已落地，v1.2.0）**：UserId/MerchantId/Role/Status/InvitedBy/JoinedAt/RemovedAt；(UserId,MerchantId) 唯一约束；StockStatus 迁移已回填（按全局角色映射 MerchantAdmin→Admin 成员、其余→Staff）。成员行状态机 Active / Removed / Suspended。
- `User.MerchantId` 单值列已标记废弃（仅兼容，成员关系以 MerchantMember 为准）。
- 鉴权语义："用户 U 能否管理商户 M" = 存在 `MerchantMember(U, M, MerchantAdmin, Active)`（查库，不看 JWT）。
- **当前商户上下文（已落地）**：`UserContextMiddleware` 解析请求头 `X-Merchant-Id`（必须是该用户的在职成员商户，否则回退缺省 = 首个 Active 成员商户）→ `context.Items["CurrentMerchantId"]`；`ICurrentUserService.CurrentMerchantId` 供各端点读取。
- **IsMerchantAdmin 恒 false 修复（已落地）**：`PermissionService.IsMerchantAdmin()` 改查成员表 + CurrentMerchantId；AddStaff/RemoveStaff/Suspend/Activate/ChangeRole 与 4 个 MerchantBearing handler 管理端校验真正生效。
- **审核门修复（已落地）**：新增 `POST /api/admin/merchants/{id}/approve`（Pending→Active）；与 verify（认证等级）分离。

### 4.3 邀请模型（StaffInvitation，已扩展）
- `Type`（Staff / Nomination）、`Status`（Pending/Accepted/Declined/Expired/Revoked，替代仅 IsCompleted bool）、`InitiatorJoins`（提名时发起人是否默认入伙为 Staff）。
- 过期：固定 7 天（`IsExpired()`）。
- 渠道无关：生成 invite code；送达（邮箱/OA、短信、站内待办）只是投递通道。
- **邀请落地页**：Taro H5 注册/登录页携带 inviteCode（signup 已支持 InviteCode→claim→JIT AssignToMerchant）。
- 服务间用户查询：API 持 sync/admin token 调 Identity 既有 `/api/account/admin/users`。

### 4.4 商户状态机
- `MerchantStatus`：Active=0 / Suspended=1 / Pending=2 / **Draft=3**（已追加；提名阶段的未生效商户，不可被 C 端检索、不被 Sync 合并）。
- 迁移：
  - 模式 A/C：申请→ Pending →(Admin approve)→ Active；拒绝 → Suspended（附原因，可重新申请；认领被拒可 `ReopenForClaim`）。
  - 模式 B（提名）：Draft →(被提名人接受并补资料)→ Pending →(Admin approve)→ Active。
- **审核门**（已修复）：`approve`（Pending→Active 生效）与 `verify`（认证等级）分离。

## 5. 登录 / 注册

### 5.1 凭据策略：密码先行，SMS 后补
- P0（已落地）：手机号（作用户名）+ 密码，走 Identity `password` grant。
- P2：SMS grant 在 Identity 已就绪（AllowCustomFlow("sms") + handler + mobile-client 权限），并发通道已可选。
- 注册即登录：signup 不返 token → BFF register 链式执行 signup + password grant，返回 access+refresh 给前端。

### 5.2 三段契约（逐字段对齐）
- Taro → BFF：
  - 注册 `POST /mobile/auth/register` { phone, password, agreeTerms }（P0）
  - 登录 `POST /mobile/auth/login` { username, password, deviceId }；`/mobile/auth/login-sms` { phone, code, deviceId }
  - 发码 `POST /mobile/auth/send-code` { phone, type=login }
  - 刷新 `POST /mobile/auth/refresh` { refreshToken, deviceId }
- BFF → Identity：
  - 所有 /connect/token 请求带 `client_id=mobile-client`、`realm=openfindbearings`、`scope=api:mobile`。
  - BFF register 映射 Identity signup：account=phone、confirmPassword=password、realm=openfindbearings、agreeTerms 由 Taro 注册页真实收集勾选后透传（**不得 BFF 硬编码 true**，合规项）。
  - sms 参数名统一 `phone`/`code`。
- BFF 自身：`Identity:Audience` 为资源名 `openfindbearings-api`；转发 API 时透传用户 access_token。
- Taro 侧：`stores/auth.ts` 已接线；login 发 `{username,password,deviceId}`；refresh 发 `{refreshToken, deviceId}`。

### 5.3 device_id 语义
- 客户端自报、服务端仅做"跨请求一致性比对"，防误用/串设备，**不防伪造**。
- 卸载重装 → storage 清空 → 新 GUID → 旧 refresh 全废 → 强制重登。
- Taro：本地随机 GUID，storage.ts 异步持久化（RN 无 getStorageSync），随登录/刷新携带；同一会话生命周期内稳定。

### 5.4 token 策略（Taro 侧）
- access_token 仅内存；refresh_token 持久化。
- 401 → 刷新 → 重放；刷新 **single-flight**（并发只刷一次）。
- 刷新失败（invalid_grant）→ 清态跳登录，不静默降级成空数据。
- access token 10 分钟、不可吊销：登出/吊销存在最长 10 分钟残余窗口。

## 6. 商户入驻（已落地）

入驻入口三种模式已实现；默认"自助当管理员"，可选"提名他人当管理员"；支持"认领存量商户"。

### 6.1 模式 A：自助当管理员（mode=self）
1. 登录用户经 `POST /api/merchant/apply`（mode=self）填商户资料+资质 → 建 Pending 商户 + 发起人 MerchantMember(Role=MerchantAdmin, Active)。
2. Admin `POST /api/admin/merchants/{id}/approve`（Pending→Active）→ 商户生效、发起人管理员生效。
3. 被拒 → 商户 Suspended（附原因）；成员行随申请流程管理，可重新申请。

### 6.2 模式 B：提名他人当管理员（mode=nominate）
1. `POST /api/merchant/nominate`：填被提名人手机号/邮箱 + 商户基础信息草稿 → 建 **Draft 商户** + 一条 `Type=Nomination, Role=MerchantAdmin` 的 StaffInvitation（`InitiatorJoins` 默认 true，发起人将入伙为 Staff）。
2. 送达：邮箱/OA、短信、站内待办。
3. 被提名人 `POST /api/merchant/nominate/{code}/accept` 补全资料 → Draft→Pending；邀请关联手机号与 JWT `phone_number` 比对（防冒领）。
4. Admin approve → Active，建双方成员行：被提名人=MerchantAdmin；发起人=MerchantStaff（InitiatorJoins=true 时）。
5. 拒绝/超时 → 提名 Status=Declined/Expired，Draft 商户失效；`GET /api/merchant/nominations/pending` 按当前手机号列出待我接受的提名。

### 6.3 认领存量商户（mode=claim）
- 搜索入口：`GET /api/merchant/claimable?keyword=&page=&pageSize=`（未被认领的爬虫来源商家）。
- 认领：`POST /api/merchant/apply`（mode=claim, claimMerchantId）→ 审核通过后申请人成为该商户 MerchantAdmin。
- 曾被拒绝的爬虫商家再次被认领：`ReopenForClaim()` 清除拒绝标记恢复待审核。

### 6.4 入驻状态查询
- `GET /api/merchant/application`：当前用户在各商户的入驻进度（待审核/已生效/已拒绝）。
- 前端"入驻状态页"据此渲染（申请中/待审核/已通过/已拒绝）。

### 6.5 管理员与团队
- 多管理员：一个商户可有多条 MerchantAdmin 成员行；任一在职 admin 可邀请/移除 admin 与 staff。
- 成员操作（商户侧，MerchantEndpoints）：
  - `GET/POST/DELETE /api/merchant/staff`
  - `POST /api/merchant/members/{userId}/suspend`（停用，保留关系可恢复）
  - `POST /api/merchant/members/{userId}/activate`（恢复）
  - `PUT /api/merchant/members/{userId}/role`（变更角色）
- 下限守卫：商户须 ≥1 Active MerchantAdmin；移除/停用将致 0 时拦截。
- 平台兜底：`POST /api/admin/merchants/{id}/members`（商户无在职管理员时平台指定/恢复）。

### 6.6 商户库存

### 6.7 商户信息维护与 Logo（v1.3.0 新增，MerchantAdmin 专属）
- 入口：商户页（已入驻分支）"信息维护"按钮，仅 `current.role === 'MerchantAdmin'` 显示。页面 `pages/merchant/profile`。
- 读：`GET /mobile/merchant/profile` → API `GET /api/merchant/profile`（按 `X-Merchant-Id` 当前商户上下文，v2.2.0 起读写同源，杜绝多商户"载 A 存 B"）。
- 写：`PUT /mobile/merchant/profile` → API `PUT /api/merchant/profile`（后端 `IsMerchantAdmin` 校验；`UpdateMerchantCommandHandler` null=保留，故"留空字段不改"）。
- Logo：`POST /mobile/merchant/logo` 选图上传，BFF 原样回 API 落库的**相对媒体键** `/uploads/merchants/logo/...`，填入表单 `logoUrl`，保存时随 `PUT /profile` 落库（不即时写）。落盘 `wwwroot/uploads/merchants/logo`（hostPath `/opt/openfindbearings/api/uploads`），与头像/执照同 API 树；渲染经 `usableImage` 拼独立媒体源 base（`mediaBaseUrl`，v1.4.0 起不再走 `/mobile/media`）。
- 说明：Logo 属"入驻后日常维护"，不放向导（入驻阶段专注资料）；`claim` 认领会保留原 `merchant.LogoUrl`（字段级 `??` 合并），管理员后续可在维护页替换。

## 7. 当前商户上下文（一人多商户）

- 移动端"商户切换器"（v1.3.0 落地）：名下多个 Active 商户时选定当前操作商户；仅一个则默认；游客/无商户隐藏。
  - **TabBar 中间商家 tab** 订阅 `useMerchantStore`（`merchants`/`currentMerchantId`/`switchMerchant`），实时显示当前商户 Logo/名称（无 Logo/加载失败回退 store 图标）；多商户时点击呼出 `MerchantSwitchSheet` 切换（取代原一次性读 `merchant_logo`/`merchant_name` 单值 storage 镜像——该镜像不随切换更新且 `merchant_logo` 从无写入源）。
  - `MerchantSwitchSheet`：`.rn.tsx` 自绘 bottom sheet（Modal，每行 Logo/首字母 + 名称 + 角色 + 当前对勾 + 底部"＋ 申请入驻其他商户"），挂载于 `app.rn.tsx` 根、命令式 `showMerchantSwitchSheet(items, currentId)` 触发；非 RN 端 `.tsx` 用 `Taro.showActionSheet` 兜底，同接口。商户页顶部胶囊复用同一 sheet。
  - 切换数据源：`GET /mobile/merchants/application`（`MerchantApplication.logoUrl`）。
- **统一 `X-Merchant-Id`**（缺省=用户唯一/首个 Active 成员行）；不采用"JWT 带 active merchant"。
- API 落点：`UserContextMiddleware` 解析 X-Merchant-Id + 校验成员 → `context.Items["CurrentMerchantId"]`；`ICurrentUserService.CurrentMerchantId`。
- BFF：ApiClient 透传 X-Merchant-Id（与 Authorization 一并透传）。
- 用户级数据（收藏/关注/历史）不受商户上下文影响，切换商户不改变它们。

## 8. 登出 / 注销账户

- **登出（移动端）**：清本地 token + `POST /connect/revocation` 吊销 refresh（/connect/logout 是浏览器 SSO 结束会话、对无 cookie 的 Taro 无意义）；mobile-client 种子须含 `Permissions.Endpoints.Revocation`。
- **令牌吊销（改密/重置/禁用/注销/登出）**：Identity 内部用 `IOpenIddictTokenManager.RevokeAsync` 编程调用。refresh 轮换 `UseRollingTokens` 暂缓。
- **刷新链路补状态校验**：`HandleRefreshTokenAsync` 补 `CheckCanLoginAsync`，禁用即时生效。
- **注销账户（用户自助，守卫前置）**：
  1. BFF 编排：先调 API "注销预检"（该用户是否为某商户唯一/最后管理员；是则阻止并提示先转让/需有 co-admin）。
  2. 预检通过 → 调 Identity 软删该 OIDC 用户 + 吊销其全部 token。
  3. 再调 API：业务用户标失效（User.Disable）+ 成员行全部置 Removed + 直接删除收藏/关注/浏览历史；商户/在售等业务数据保留、仅解除归属。
  4. 补偿：第 3 步失败时 Identity 侧 RestoreAsync 回滚软删。

## 11. 关键时序（文字）

- 注册登录（已通）：Taro 输手机号+密码+勾选协议 → BFF /auth/register（signup→password grant）→ Identity 建 OIDC 用户+发 token（aud=openfindbearings-api）→ Taro 存（access 内存/refresh 持久）→ 首个业务请求 → API UserContextMiddleware JIT 建业务用户（Individual）。
- 入驻模式 A（已落地）：登录用户填资料 → /api/merchant/apply(self) → API 建 Pending 商户 + 发起人 MerchantAdmin 成员行 → Admin approve → Active。
- 入驻模式 B（已落地）：发起人填被提名手机/邮箱 → /api/merchant/nominate → 建 Draft 商户 + Nomination 邀请 → 送达 → 被提名人经 /api/merchant/nominate/{code}/accept 补资料 → Draft→Pending → approve → 被提名人 Admin、发起人 Staff（按 InitiatorJoins）。
- 邀请成员：admin 输邮箱/手机+角色 → 生成邀请 → 送达 → 对方经 Taro H5 注册页带 code 接受 → 建/复用 MerchantMember。
- 注销：设置→注销 → 二次确认 → BFF 预检（唯一/最后管理员守卫）→ Identity 软删+吊销 → API 标失效+成员 Removed+删个人数据；失败补偿 restore。

## 12. 边界规则汇总

1. 认证以 Identity 为准；业务以 API 为准；单向同步（互不反写/反查）。
2. 业务鉴权查 API 权限表/成员表，不信 JWT role claim。
3. 商户须 ≥1 Active 管理员；移除能力与守卫同批；0 时平台超管兜底。
4. 一人可多商户；角色按 (用户,商户) 维度；商户级操作带 X-Merchant-Id；用户级数据不受影响。
5. 提名可被拒绝/超时失效（Draft 商户随之失效）；发起人默认 Staff、可"仅推荐不加入"。
6. 注销守卫前置；注销后个人数据（收藏/关注/历史）直接删，业务数据保留解绑。
7. device_id 仅防误用不防伪造；短信未就绪前用邮箱/邀请码，不卡死。
8. 保护 OpenIddict：吊销用 Manager API 编程调用，不改 grant/端点/handler/租户模型；refresh 轮换暂缓。
