# 移动端登录与商户入驻设计

- 版本：v1.1.0
- 状态：讨论稿（待评审，未实施）
- 适用范围：OpenFindBearings.Taro（H5/RN/小程序）、OpenFindBearings.Mobile（BFF）、OpenFindBearings.Identity（认证中心）、OpenFindBearings.Api（业务与商户模型）、OpenFindBearings.Admin（后台审核/成员管理）
- 变更记录：
  - v1.0.0 首次成文。
  - v1.1.0 依 general 子代理审查修订：修正商户成员迁移映射（按现有角色而非一律 Admin）；确立"API 业务鉴权查库、不用 JWT role claim"（修 IsMerchantAdmin 恒 false）；删除"JWT 带 active merchant"备选、统一 X-Merchant-Id；注销改为守卫前置（预检）；令牌吊销改用 IOpenIddictTokenManager 编程调用（不碰 OpenIddict 配置），refresh 轮换暂缓；注册契约对齐 Identity signup（account/confirmPassword/realm/agreeTerms）+ BFF 链式 signup+password grant；补认领存量商户 mode=claim（预留）；邀请落地页改指 Taro H5 注册页带 inviteCode；补商户审核 Approve 门（现状 bug）；成员表状态机收敛（成员行仅接受时创建、复用 Removed 行）；MerchantStatus 增 Draft；注销后个人数据直接删（热门不依赖）；to-do 重排为"入驻整体最后"。

## 1. 背景与目标

移动端要落地"登录 / 登出 / 注销账户"与"商户入驻 / 团队管理"。现状：认证与业务用户分两库（Identity 拥有认证用户、API 拥有业务用户，靠 sub 关联），注册/登录入口（Taro→BFF→Identity）未打通、短信发送是半成品、商户成员是"一人一商户"单值列、且存在两处今天就坏的问题（商户审核门缺失、IsMerchantAdmin 恒 false）。本文给出可落地设计与分期，**普通用户注册登录优先，商户入驻整体放最后**。

核心原则：
1. 认证事实源永远在 Identity；业务事实在 API；同步方向单向（API 不反写 Identity，Identity 不查 API）。
2. 用户由"注册"产生（Taro 自助注册），不是后台 create。
3. 一个自然人（一个 sub）可属于多个商户、在每个商户有不同角色。
4. 商户不设唯一管理员，可多管理员；须 ≥1 管理员，平台超管作零管理员兜底。
5. 送达渠道与邀请机制解耦（邀请码/链接为核心，邮箱/OA 优先、短信/站内补充），不被短信网关卡死。
6. **保护 OpenIddict**：不改 grant/端点拓扑/租户模型/handler 逻辑；令牌吊销等只用 OpenIddict 提供的 Manager API 编程调用。

## 2. 术语与角色

- 认证用户（OIDC User）：Identity 拥有，手机号为用户名，持有 sub。
- 业务用户（Business User）：API 拥有，AuthUserId=sub 关联，首次带 token 调 API 时 JIT 创建。
- **鉴权事实源分工（重要，纠正现状 bug）**：Identity 自管理台用 token 里的 role；**OpenFindBearings 业务鉴权不用 token role claim，一律查 API 自己的权限表/成员表动态判定**。JWT 的 role claim 不作为业务鉴权依据。
- 平台级角色（API 全局 RBAC）：Individual、Admin、SuperAdmin。
- 商户域角色（按商户维度，存于成员行）：MerchantAdmin、MerchantStaff。
- 商户成员（Merchant Member）：(用户, 商户, 商户域角色, 状态) 的一条关系。

## 3. 用户两档模型

- 档 1 普通用户：注册并登录后，收藏 / 关注 / 浏览历史解锁可用；可发起"商户入驻"。
- 档 2 商户成员：通过入驻或受邀，成为某商户的 MerchantAdmin / MerchantStaff，管理该商户在售商品、团队、资料。

两档是"同一 sub 用户逐步获得角色/成员关系"，不是两类账户。一个 sub 可同时是：普通用户 + A 商户管理员 + B 商户员工。用户级数据（收藏/关注/历史）挂 UserId、与商户上下文无关；商户级操作才需当前商户上下文。

## 4. 数据模型

### 4.1 Identity 侧（认证）
- 维持现状：OIDC 用户、client/scope/permission、device_id claim、realm→TenantId。
- **不改 OpenIddict grant/端点/handler/租户模型**。安全项仅通过 Manager API 编程实现（见 8）。
- 注册入口已存在：`POST /api/Account/signup`（AllowAnonymous），请求体 `SignUpRequest{ account, password, confirmPassword(必填), agreeTerms(必须 true), realm(必填), inviteCode? }`；signup 只返回 UserResponse、**不返回 token**。

### 4.2 API 侧（业务与商户）
新增成员表（多对多，成为"谁属于哪个商户、在该商户什么角色"的唯一事实源）：

| 字段 | 说明 |
|---|---|
| Id | 主键 |
| UserId | 业务用户 Id（sub 映射后的 API User） |
| MerchantId | 商户 Id |
| Role | MerchantAdmin / MerchantStaff |
| Status | Active / Removed（**不设 Invited**：待接受只存 StaffInvitation，成员行仅在接受时创建） |
| InvitedBy / JoinedAt / RemovedAt | 审计 |
| 唯一约束 | (UserId, MerchantId) 唯一；**再受邀复用 Removed 行**（翻回 Active、更新 Role/InvitedBy），不插第二行 |

变更：
- 废弃 `User.MerchantId` 单值列，迁移为 MerchantMember 行。**迁移映射按现有全局角色**（不是一律 Admin）：
  - 持 MerchantAdmin 全局角色 → MerchantMember(Role=MerchantAdmin)；
  - 持 MerchantStaff 全局角色 → MerchantMember(Role=MerchantStaff)；
  - 有 MerchantId 但无商户角色（invite_code JIT 路径）→ MerchantMember(Role=MerchantStaff) + **输出人工复核清单**；
  - SeedData 里有 MerchantAdmin 角色但 MerchantId 为空的 → 不迁移，单独列出。
- 商户域角色从"全局用户角色"迁到"成员行角色"；平台级角色仍走全局 RBAC。
- 鉴权语义："用户 U 能否管理商户 M" = 存在 `MerchantMember(U, M, MerchantAdmin, Active)`（查库，不看 JWT）。
- **迁移影响面（T2/T3 必须逐个改造，不止 DeriveRateLimitUserType）**：UserContextMiddleware（限流档位）、PermissionService（IsMerchantStaffAsync / CanManageBearingAsync / IsMerchantAdmin）、GetMerchantByUserIdQueryHandler（MerchantEndpoints 8 个端点靠它定位商户）、AddStaff/RemoveStaffCommandHandler（现"已是其他商家员工"=一人一商户硬约束；RemoveStaff 无角色移除、无最后管理员守卫）、CreateUserFromAuthCommandHandler、4 个 MerchantBearing handler（PutOnShelf/TakeOffShelf/UpdateMerchantBearing/SetPriceVisibility 各查 currentUser.MerchantId）、GetUserProfileQueryHandler、GetDashboardStatsQueryHandler、User/Merchant 聚合与 EF 配置。
- **同批修复 IsMerchantAdmin 恒 false**：改为查成员表，AddStaff/RemoveStaff 的管理员校验才真正生效。

### 4.3 邀请模型（扩展现有 StaffInvitation）
- `Role` 字段已存在（string），枚举取值 Admin/Staff。
- 新增 `Type`（Staff / Nomination）、`Status`（Pending/Accepted/Declined/Expired/Revoked，替代现有仅 IsCompleted bool）、`InitiatorJoins`（提名时发起人是否默认入伙为 Staff）。
- 过期：StaffInvitation 现有 IsExpired 固定 7 天；提名类可单设时效。
- 渠道无关：生成 invite code / 带 token 链接；送达（邮箱/OA、短信、站内待办）只是投递通道。
- **邀请落地页修正（现状坏）**：现有链接指向 `{Identity}/register?code=` 而 Identity 无 /register 页 → 改为指向 **Taro H5 注册/登录页携带 inviteCode**（signup 已支持 InviteCode→claim→JIT AssignToMerchant）。API→Identity 的服务间用户查询（by-phone/by-email）端点不存在 → 改为 API 持 sync/admin token 调 Identity 既有 `/api/account/admin/users`，或 Identity 补服务间查询端点（P4 邀请阶段定）。

### 4.4 商户状态机
- `MerchantStatus` 现有 Active=0 / Suspended=1 / Pending=2；**追加 Draft=3**（提名阶段的未生效商户，不可被 C 端检索、不被 Sync 合并；枚举追加向后兼容）。
- 迁移：Draft →(被提名人接受并补资料)→ Pending →(Admin approve)→ Active；Draft →(拒绝/超时)→ 失效（删除或标记）。
- **审核门（现状 bug，必修）**：现无任何代码调用 `Merchant.Approve()`；须补 approve 命令/端点（Pending→Active），与 verify（置 IsVerified+Grade）**分离**：approve=审核通过使其生效，verify=认证等级。被拒后重新申请的处置（新建 or 回 Pending）在入驻阶段定。

## 5. 登录 / 注册

### 5.1 凭据策略：密码先行，SMS 后补
- P0：手机号（作用户名）+ 密码，走 Identity `password` grant，不依赖短信网关。
- P2：SMS grant **在 Identity 已就绪**（AllowCustomFlow("sms") + handler + mobile-client 权限），缺口仅"真实发送通道 + BFF 参数名 + Taro UI"；开发态固定验证码 + 日志输出。
- 注册即登录：signup 不返 token → **BFF register 链式执行 signup + password grant**，返回 access+refresh 给前端。

### 5.2 三段契约（逐字段对齐）
- Taro → BFF：
  - 注册 `POST /mobile/auth/register` { phone, password, agreeTerms }（P0）；{ phone, code }（P2）
  - 登录 `POST /mobile/auth/login` { username, password, deviceId }；`/mobile/auth/login-sms` { phone, code, deviceId }
  - 发码 `POST /mobile/auth/send-code` { phone, type=login }（**type 统一 login**：sms grant 固定按 login 校验且"登录即注册"，register 类型 P2 再议）
  - 刷新 `POST /mobile/auth/refresh` { refreshToken, deviceId }
- BFF → Identity（现状断点，须补全）：
  - 所有 /connect/token 请求带 `client_id=mobile-client`（公开客户端自报）、`realm=openfindbearings`（否则 password/sms handler 租户关直接拒绝）、`scope=api:mobile`（否则 token 无 aud=openfindbearings-api、API 全 401）。
  - BFF register 映射 Identity signup：account=phone、confirmPassword=password、realm=openfindbearings、agreeTerms 由 Taro 注册页真实收集勾选后透传（**不得 BFF 硬编码 true**，合规项）。
  - sms 参数名统一 `phone`/`code`（现 BFF 发 username/sms_code，Identity 读 phone/code）。
- BFF 自身：`Identity:Audience` 由 `api:mobile` 改为资源名 `openfindbearings-api`；转发 API 时**透传用户 access_token**（现传 null）。
- Taro 现状修正：`stores/auth.ts` 是死代码需接线；login 现发 `{phone,password}` 须改 `{username,password,deviceId}`；`config.ts` 的 LOGIN/REGISTER/REFRESH 路径已存在（核对即可，并补 LOGIN_SMS/SEND_CODE）；refresh 现只发 `{refreshToken}` 须补 deviceId（否则 BFF FormUrlEncoded 对 null 抛异常）。

### 5.3 device_id 语义
- 客户端自报、服务端仅做"跨请求一致性比对"，防误用/串设备，**不防伪造**（隐私文案不得承诺"防盗号"）。
- 卸载重装 → storage 清空 → 新 GUID → 旧 refresh 全废 → 强制重登（可接受，文档写明）。
- Taro：本地随机 GUID，storage.ts 异步持久化（RN 无 getStorageSync），随登录/刷新携带；同一会话生命周期内稳定（登录不无条件覆盖）。

### 5.4 token 策略（Taro 侧）
- access_token 仅内存（纠正 request.ts 落盘）；refresh_token 持久化。
- 401 → 刷新 → 重放；刷新 **single-flight**（并发只刷一次，避免共用一次性 refresh_token 竞态）。
- 刷新失败（invalid_grant）→ 清态跳登录，**不静默降级成空数据**。
- access token 10 分钟、不可吊销：登出/吊销存在最长 10 分钟残余窗口（行业常规，文档写明）。

## 6. 商户入驻（整体最后做；本期只留预留）

入驻入口两种模式，默认"自助当管理员"，可选"提名他人当管理员"；另预留"认领存量商户"。

### 6.1 模式 A：自助当管理员（默认）
1. 登录用户点"申请入驻"，填商户资料+资质 → 建 Pending 商户 + 发起人 MerchantMember(Role=MerchantAdmin, Active)。
2. Admin 后台 approve（Pending→Active，见 4.4）→ 商户生效、发起人管理员生效。
3. 被拒 → 成员行置 Removed、商户回 Draft/删除（入驻阶段定）。

### 6.2 模式 B：提名他人当管理员
1. 登录用户点"申请入驻"选"指定他人为管理员"，填被提名人手机号/邮箱 + 商户基础信息草稿 → 建 **Draft 商户** + 一条 `Type=Nomination, Role=MerchantAdmin` 的 StaffInvitation（发起人 InitiatorJoins 默认 true）。
2. 送达被提名人（邮箱/OA 优先、短信/站内补充）：已注册→登录后见"待办提名"；未注册→经邀请链接落 Taro H5 注册页带 code。
3. 被提名人接受 → **由被提名人补全资料** → Draft→Pending → Admin approve → Active。
4. 审核通过时（**非提名时**）建成员行：被提名人=MerchantAdmin；发起人=MerchantStaff（InitiatorJoins=true 时），否则不建。
5. 拒绝/超时 → 提名 Status=Declined/Expired，Draft 商户失效；发起人可换人提名或改自助。

### 6.3 认领存量商户（mode=claim，预留、逻辑后细化）
- 场景：Sync 持续灌入爬虫商户，自助入驻只新建会与爬虫数据重复。
- 预留：apply 契约含 `mode=self|nominate|claim` + `claimMerchantId`；入驻时先按名称/统一社会信用代码查重，命中则引导认领（claim 后申请人成该商户 MerchantAdmin），或新建并将爬虫重复项标废弃。具体逻辑入驻阶段细化。

### 6.4 管理员与团队
- 多管理员：一个商户可有多条 MerchantAdmin 成员行；任一在职 admin 可邀请/移除 admin 与 staff（建议简单模型；若要更严可"仅首个 admin/owner 加 admin"，入驻阶段定）。
- 下限守卫：商户须 ≥1 Active MerchantAdmin；移除/离职/注销将致 0 时拦截。**移除能力与守卫必须同批交付**（避免中间窗口删成 0 管理员）。
- 平台兜底：异常致 0 管理员时，平台超管在 Admin 后台指定新管理员（预留权限 merchant.member.manage）。

## 7. 当前商户上下文（一人多商户）

- 移动端"商户切换器"：名下多个 Active 商户时选定当前操作商户；仅一个则默认；游客/无商户隐藏。
- **统一 `X-Merchant-Id`**（缺省=用户唯一/首个 Active 成员行）；**不采用"JWT 带 active merchant"**（违反单向同步、切换需重签 token）。
- API 落点：UserContextMiddleware 解析 X-Merchant-Id + 校验"该用户是该商户 Active 成员" → `context.Items["CurrentMerchantId"]`；GetMerchantByUserIdQuery 改按上下文取商户；4.2 影响面清单逐个改造。
- BFF：ApiClient 透传 X-Merchant-Id（现仅透传 Authorization）。
- 用户级数据（收藏/关注/历史）不受商户上下文影响，切换商户不改变它们。

## 8. 登出 / 注销账户

- **登出（移动端）**：清本地 token + `POST /connect/revocation` 吊销 refresh（`/connect/logout` 是浏览器 SSO 结束会话、对无 cookie 的 Taro 无意义）。前置：mobile-client 种子须含 `Permissions.Endpoints.Revocation`（这是客户端种子数据调整，非 OpenIddict handler 改动）。
- **令牌吊销（改密/重置/禁用/注销/登出）**：Identity 内部用 `IOpenIddictTokenManager.RevokeAsync` **编程调用**（不改 grant/端点/handler）。refresh 轮换 `UseRollingTokens` **暂缓**（属 server 配置改动，鉴于保护 OpenIddict 的约束先不加；靠显式吊销 + 现有时效堵主要洞，将来单独评审再加）。
- **刷新链路补状态校验**：`HandleRefreshTokenAsync` 补 `CheckCanLoginAsync`（与 authorization_code/password/sms 对齐），禁用即时生效。
- **注销账户（用户自助，守卫前置）**：
  1. BFF 编排：先调 API "注销预检"（该用户是否为某商户唯一/最后管理员；是则阻止并提示先转让/需有 co-admin）。**降级版（成员表落地前）**：有商户归属（MerchantId 非空）即阻止注销并提示。
  2. 预检通过 → 调 Identity 软删该 OIDC 用户 + 吊销其全部 token。
  3. 再调 API：业务用户标失效（User.Disable）+ 成员行全部置 Removed + **直接删除**收藏/关注/浏览历史（已核实热门=ViewCount/IsVerified，不依赖这些个人数据，删除安全且合规）；商户/在售等业务数据保留、仅解除归属。
  4. 补偿：第 3 步失败时 Identity 侧 RestoreAsync 回滚软删。

## 11. 关键时序（文字）

- 注册登录（P0）：Taro 输手机号+密码+勾选协议 → BFF /auth/register（signup→password grant）→ Identity 建 OIDC 用户+发 token（aud=openfindbearings-api）→ Taro 存（access 内存/refresh 持久）→ 首个业务请求 → API UserContextMiddleware JIT 建业务用户（Individual）。
- 入驻模式 A（P4）：登录用户填资料 → /merchants/apply(self) → API 建 Pending 商户 + 发起人 MerchantAdmin 成员行 → Admin approve → Active。
- 入驻模式 B（P4）：发起人填被提名手机/邮箱 → /merchants/nominate → 建 Draft 商户 + Nomination 邀请 → 邮箱送达 → 被提名人（注册/登录）接受 → 补资料 → Draft→Pending → approve → 被提名人 Admin、发起人 Staff（按 InitiatorJoins）。
- 邀请成员（P4）：admin 输邮箱/手机+角色 → 生成邀请 → 送达 → 对方经 Taro H5 注册页带 code 接受 → 建/复用 MerchantMember。
- 注销（P1 降级 / P4 完整）：设置→注销 → 二次确认 → BFF 预检（唯一/最后管理员守卫）→ Identity 软删+吊销 → API 标失效+成员 Removed+删个人数据；失败补偿 restore。

## 12. 边界规则汇总

1. 认证以 Identity 为准；业务以 API 为准；单向同步（互不反写/反查）。
2. 业务鉴权查 API 权限表/成员表，不信 JWT role claim。
3. 商户须 ≥1 Active 管理员；移除能力与守卫同批；0 时平台超管兜底。
4. 一人可多商户；角色按 (用户,商户) 维度；商户级操作带 X-Merchant-Id；用户级数据不受影响。
5. 提名可被拒绝/超时失效（Draft 商户随之失效）；发起人默认 Staff、可"仅推荐不加入"。
6. 注销守卫前置；注销后个人数据（收藏/关注/历史）直接删，业务数据保留解绑。
7. device_id 仅防误用不防伪造；短信未就绪前用邮箱/邀请码，不卡死。
8. 保护 OpenIddict：吊销用 Manager API 编程调用，不改 grant/端点/handler/租户模型；refresh 轮换暂缓。
